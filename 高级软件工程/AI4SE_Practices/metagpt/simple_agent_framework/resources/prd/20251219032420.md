## Product Goals

- 降低多智能体系统开发门槛，使开发者能快速构建原型
- 提供灵活可扩展的架构，支持高度自定义的智能体行为与交互
- 确保框架核心简洁稳定，专注于智能体调度与LLM通信

## User Stories

- 作为一名AI应用开发者，我希望快速集成多个具备不同角色的智能体（如分析师、编码员），以协作完成一个复杂任务（如生成一份市场报告），这样我就能验证多智能体协作的可行性。
- 作为一名研究人员，我希望能够自定义智能体的思考模版、工具函数以及记忆方式，这样我就能实验不同的智能体架构对任务完成效果的影响。
- 作为一名学生，我希望框架提供清晰的示例和文档，让我能通过几行代码就启动一个多智能体对话，这样我就能快速学习多智能体系统的概念。
- 作为一个项目负责人，我希望框架能清晰管理智能体间的对话历史和上下文，以便于调试和追踪任务执行链路。

## Competitive Analysis

- LangChain/LangGraph：功能全面，生态庞大，但学习曲线陡峭，对于只想快速使用多智能体的用户来说过于复杂。
- AutoGen（by Microsoft）：支持复杂的多智能体对话模式，但配置繁琐，且重度绑定其特定的对话流程。
- CrewAI：面向“智能体协作团队”概念，角色定义清晰，但框架约定较多，自定义灵活性相对受限。
- Haystack（by deepset）：更侧重于文档检索与问答管道，其智能体能力作为子模块，并非纯粹为多智能体对话设计。
- Semantic Kernel（by Microsoft）：强在规划与插件，但多智能体间的自然语言对话并非其首要焦点。
- 简易自实现脚本：完全自由，但缺乏通用结构，每次项目都需要重复实现基础通信、历史管理等功能。
- ChatGPT/API 直接调用：极度灵活，但需要开发者从零搭建所有协调逻辑，开发效率低。

## Requirement Analysis

本项目的核心是构建一个轻量、模块化的Python多智能体框架。关键需求分析如下：
1.  **智能体抽象**：需要定义一个基础智能体类（Agent），包含名称、系统提示词、LLM客户端等属性，以及一个核心的“响应生成”方法。
2.  **LLM集成**：必须无缝集成OpenAI API（或兼容API），作为智能体的“大脑”。需要处理API密钥管理和基本调用。
3.  **自定义支持**：框架需允许用户通过继承或组合的方式，轻松创建自定义智能体。自定义点应包括：系统角色指令、调用的工具集、对话历史处理方式。
4.  **多智能体协调**：需要提供一种机制（如一个“协调器”或“会话”类）来组织多个智能体之间的对话。最简单的形式是顺序对话，但也应为更复杂的路由（如基于条件的智能体选择）留出扩展空间。
5.  **对话历史管理**：框架应自动维护和传递对话上下文（消息列表），确保每个智能体能够基于历史进行回复。
6.  **简洁性与可用性**：API设计应直观，让用户通过少量代码即可完成智能体定义、组装和运行。避免引入不必要的复杂概念。

## UI Design draft

这是一个Python代码库框架，没有传统图形用户界面（GUI）。其“用户界面”即面向开发者的API设计与使用体验。

**1. 代码结构（核心模块）:**
- `agent.py`: 定义 `BaseAgent` 和 `SimpleAgent` 类。
- `llm.py`: 封装 `OpenAIClient`。
- `session.py`: 定义 `Session` 或 `Team` 类，管理多个Agent的对话流。
- `tools.py`: （可选）提供工具装饰器和注册机制。
- `examples/`: 存放多种用法的示例脚本。

**2. 使用方式示例（代码即UI）:**
```python
from simple_agent_framework import SimpleAgent, Session

# 定义智能体
analyst = SimpleAgent(name="分析师", system_prompt="你是一位资深市场分析师...")
coder = SimpleAgent(name="程序员", system_prompt="你是一位Python专家...")

# 创建会话并添加智能体
team_session = Session(agents=[analyst, coder])

# 运行一个多轮任务
result = team_session.run(task="请协作分析当前AI趋势并生成一段示例代码。")
print(result)
```

**3. 风格与布局:**
- **风格**: 代码设计追求清晰、符合Python惯例（如PEP8）。类和方法命名直观（如 `Agent.run`, `Session.run`）。
- **布局**: 库的导入和使用应线性、直观，让用户感觉是在“组装”智能体，而非配置复杂系统。

## Anything UNCLEAR

需求整体清晰。需要与用户进一步确认的细节包括：
1.  对于“自定义智能体”的具体深度期望？例如，是仅自定义提示词和基础参数，还是需要支持完全覆盖消息处理流程、自定义记忆模块等。
2.  智能体间的通信模式，最初版本是否仅支持简单的轮流发言（广播式），还是需要支持更复杂的定向通信（如A只与B对话）。
3.  是否必须仅支持OpenAI官方API，还是也需要考虑兼容其他提供OpenAI格式接口的服务（如Azure OpenAI, 本地部署的兼容模型）。
当前计划将基于最核心的需求（简单、可定制、OpenAI）进行设计，并为上述扩展点预留接口。
