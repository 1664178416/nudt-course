# 多智能体系统在软件工程中的应用研究

---

## 1. 引言与研究动机

### 1.1 研究背景：从单点工具到整体编排

在本次高级软件工程课程的调研初期，我们观察到现有的 AI 辅助工具大多集中在软件开发的**特定孤立阶段**。例如，Copilot 专注于代码补全，各类单元测试生成工具专注于测试阶段。

然而，真实的软件工程是一个**长链路、高耦合**的系统性过程。
**核心问题**：现有的解决方案是分散的。需求分析、架构设计、代码编写、测试验证往往需要在不同的工具间切换，导致上下文（Context）在流转中丢失，人工协同的成本依然很高。

### 1.2 解决方案：多智能体系统 (MAS)

鉴于此，本小组**转换了调研思路**，从关注单一工具转向关注**整体解决方案**。我们提出利用 **多智能体系统 (Multi-Agent Systems)** 对软件工程进行整体编排。

通过大模型（LLM）的规划能力，我们可以模拟一个完整的软件开发团队：

* **产品经理智能体 (PM Agent)**：负责理解模糊需求，输出标准文档。
* **架构师智能体 (Architect Agent)**：负责系统设计，划分模块与接口。
* **开发者智能体 (Developer Agent)**：负责编写具体业务代码。
* **测试员智能体 (QA Agent)**：负责编写测试用例，保证质量。

## 2. 核心框架与平台调研综述

为了寻求最优的智能体编排方案，本研究小组对当前 GitHub 上高星的开源框架及业界领先的应用平台进行了深度调研。根据**抽象层级**与**交付形态**的差异，我们将调研对象划分为“底层开发框架”与“应用级协作平台”两类。

### 2.1 底层开发框架 (Developer Frameworks)

此类工具提供原子化的智能体构建能力与通信协议，主要面向具备编码能力的开发者，用于构建高定制化的多智能体系统 (MAS)。

#### **1. AutoGen (Microsoft)**

* **核心定位**：**基于对话范式的多智能体编排框架 (Conversational Orchestration Framework)**
* **技术特性**：
* **对话即计算**：采用“可对话代理 (Conversable Agent)”架构，将工具调用、记忆检索及逻辑推理统一封装为消息传递接口。
* **灵活拓扑**：支持构建复杂的通信拓扑结构，包括双人协作、群组聊天 (GroupChat) 及分层对话。
* **人机回环 (Human-in-the-loop)**：内置人类介入机制，允许在自动化流程的关键节点插入人工反馈，修正模型推理路径。


* **综合评价**：
* **优势**：灵活性极高，适用于需要复杂交互逻辑和非确定性流程的实验性任务。
* **局限**：状态管理较为发散，对于严格遵循 SOP 的工程任务，需要大量的 Prompt 工程调优。



#### **2. MetaGPT (DeepWisdom)**

* **核心定位**：**基于 SOP 的软件工程专用多智能体框架 (SOP-based MAS for SE)**
* **技术特性**：
* **流程标准化 (Code = SOP)**：将软件工程的标准作业程序 (Standard Operating Procedure) 映射为智能体协作流，预设了产品经理、架构师、工程师等标准角色。
* **结构化通信**：摒弃纯自然语言对话，强制智能体通过标准化文档（如 PRD、类图、API 接口定义）共享上下文，显著降低了信息熵减。


* **综合评价**：
* **优势**：在端到端软件开发场景下表现出极高的稳定性与可用性，能够生成结构完整的项目仓库。
* **局限**：框架抽象度较高，角色与流程相对固化，扩展至非软件工程领域的通用性较弱。



#### **3. smolagents (Hugging Face)**

* **核心定位**：**代码驱动的轻量级智能体构建库 (Code-Centric Agent Library)**
* **技术特性**：
* **代码即思维 (Code as Thought)**：不同于基于 JSON 的工具调用范式，该框架让 LLM 直接生成并执行 Python 代码来进行推理与动作，提升了逻辑表达的精确度。
* **极简抽象**：核心逻辑代码量极少（<1000 LOC），去除了复杂的中间件抽象，提供最底层的 ReAct 模式实现。


* **综合评价**：
* **优势**：透明度与可解释性极高，执行效率高，非常适合学术研究、算法验证及构建本地化的小型智能体。
* **局限**：缺乏内置的高级多智能体编排模式（如群聊、层级调度），开发者需自行实现复杂的协作逻辑。

### 2.2 应用级协作平台 (Application Platforms)

此类工具将智能体能力封装为 SaaS/PaaS 产品，面向终端用户提供开箱即用的解决方案。

#### **4. Thingo (武汉大学/思高科技)**

* **核心定位**：**基于动态调度的通用智能体协作平台 (Dynamic Agent Collaboration Platform)**
* **技术特性**：
* **动态组队 (Dynamic Coalition)**：基于语义理解自动拆解用户意图，从智能体库中动态调度文案、数据、排版等异构 Agent 组成临时任务团队。
* **领域适配**：针对中文语境下的政企办公、公文处理及复杂工作流进行了深度优化，具备较强的垂直领域知识库集成能力。


* **综合评价**：
* **优势**：极大地降低了多智能体协作的使用门槛，在文档处理与办公自动化场景具有显著优势。
* **局限**：作为闭源平台，用户难以介入底层逻辑修改，定制化能力受限于平台预设。



#### **5. 百度秒哒 (Baidu)**

* **核心定位**：**生成式零代码应用开发平台 (Generative No-Code Platform)**
* **技术特性**：
* **Prompt-to-App**：基于文心大模型构建的多模型混合架构 (MoE)，后台集成前端生成、后端逻辑、数据库设计等专用模型。
* **全栈自动化**：实现了从自然语言需求到可运行 Web 应用的全链路自动化，覆盖了 UI 设计、逻辑编写与云端部署。


* **综合评价**：
* **优势**：将应用开发的边际成本降至最低，非常适合非技术人员进行快速原型验证 (MVP) 与展示型应用开发。
* **局限**：生成的代码通常为“黑盒”或难以二次维护，不具备系统级软件工程所需的复杂逻辑处理与持续迭代能力。

## 3. 关键技术深钻：smolagents

虽然我们调研了多个框架，但我们重点深入研究了 **smolagents**，原因如下：

1. **极简与透明**：相比于其他重型框架，smolagents 的核心代码逻辑非常少，我们阅读了其源码，发现其主要基于 **ReAct (Reason + Act)** 模式进行编排。
2. **实现机制**：对于一个任务，主模型会先将其分解为多个子任务，然后编排不同的工具去执行。每次执行的结果会回馈给模型，形成闭环。
3. **易用性**：接口清晰，学习成本最低。虽然它可能不是功能最全面的，但在理解 Agent 本质逻辑上是最好的教材。

**后续计划**：在接下来的作业任务中，我们小组打算在 smolagents 框架的基础上进行二次开发。

## 4. 应用场景设想与挑战

### 4.1 典型场景：代码开发与审查闭环系统

我们构想了一个双智能体对抗系统：

1. **输入**：用户需求。
2. **开发者智能体**：调用工具生成初版代码。
3. **审查者智能体**：根据代码规范、安全规则进行扫描，生成审查报告。
4. **迭代**：开发者根据报告修改代码，这是一个反复迭代、优化的过程，直到通过审查。

### 4.2 核心优势

* **分而治之**：将复杂问题拆解。
* **专业分工**：每个智能体自带不同工具（如 Web 搜索、数据库连接）。
* **自动化**：实现 7x24 小时不间断工作。

### 4.3 面临挑战

* **开销问题**：多智能体反复对话会导致 Token 消耗巨大。
* **上下文窗口**：随着项目变大，LLM 的窗口容易溢出。
* **死循环**：智能体之间可能陷入互相推诿或无法达成一致的僵局。
