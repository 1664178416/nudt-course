## 第一部分：引言与研究背景

### 1.1 调研动机与问题提出

在软件工程的实践中，我们长期面临一个核心矛盾：**软件开发是一项高度系统化的团队协作工程，但现有的 AI 辅助工具大多只聚焦于开发链路中的某个孤立节点**。例如，GitHub Copilot 专注于代码补全，JetBrains AI Assistant 侧重于 IDE 内的智能提示，Diffblue Cover 则只关注 Java 单元测试的自动生成。这种"单点突破"的模式虽然在各自的领域都取得了显著成效，但它并没有从根本上改变软件开发中"上下文在工具间流转时大量丢失、人工协同成本居高不下"的困境。

一个完整的软件项目，从用户的一句模糊需求开始，到最终可靠运行在生产环境上，中间需要经历需求分析、系统设计、架构评审、编码实现、单元测试、集成测试、代码审查、部署运维等一系列紧密耦合的阶段。每一个阶段的输出都是下一个阶段的输入，信息的完整性和精确性至关重要。如果AI只在"编码"这一个环节提供帮助，那么它对整体研发效率的提升终究是有限的。

基于这一深刻洞察，本小组**转换了调研思路**，从关注单一的、工具化的 AI 辅助能力，转向了关注**整体解决方案**——即利用**多智能体系统（Multi-Agent Systems, MAS）**对软件工程的全生命周期进行整体编排与自动化。

- **匿名成员**：主要参与 `smolagents_app` 中关于网页端应用快速生成与可视化呈现的代码开发工作。同时在调研报告中负责对比其他多智能体框架（如 AutoGen、MetaGPT）的运行机制，提炼与本组开发工作的异同点。
- **匿名成员**：主要参与 `smolagents_app` 底层运行机制的测试与验证工作，负责处理系统内的 API 调用对接和报错排查。在调研报告中负责细化 smolagents 极简架构、安全沙箱和双核引擎特性的详细评估说明。
- **匿名成员**：主要负责 `smolagents_app` 的测试用例设计以及系统边界能力的探索测试（如算法演示、2048 游戏生成的黑盒测试）。在调研报告中负责撰写应用级协作平台（如秒哒、Thingo）的使用体验和局限性对比。

### 1.3 多智能体系统（MAS）的定义与核心价值

多智能体系统（MAS）是由多个自主个体（智能体）组成的系统，这些智能体在共享环境中相互作用、通信、协作或竞争，以完成任务或解决问题。在大语言模型（LLM）驱动的场景下，其核心公式可以概括为：

> **多智能体 = 智能体 + 环境 + 标准流程（SOP） + 通信 + 经济**

其中，每一个智能体自身也是一个复合体：

> **智能体 = 大语言模型（LLM） + 观察 + 思考 + 行动 + 记忆**

将 MAS 引入软件工程的核心价值，在于它能够通过**去中心化的专业分工与协作**，模拟一个完整的人类研发团队。例如：
- **产品经理智能体**：负责理解用户的模糊需求，输出结构化的产品需求文档（PRD）。
- **架构师智能体**：根据 PRD 进行系统设计，划分模块、定义接口与数据结构。
- **开发者智能体**：根据设计文档编写具体的业务实现代码。
- **测试员智能体**：为生成的代码编写测试用例，执行并报告结果。

这种模式使得一个复杂的软件项目得以被系统性地分解和自动执行，并且每一步的输出都是结构化的、可供下游直接消费的"文档级"交付物，从而最大程度减少了信息在流转中的损耗。

### 1.4 多智能体在软件工程（SE）中的典型应用场景

根据我们的调研和文献分析，MAS 在 SE 中的应用已基本覆盖了软件开发与维护的全流程，其主要场景可归纳为：

1. **端到端软件开发与维护**：这是最贴切地模拟现实世界软件团队的场景。通过角色分工，一个宏观目标（如"开发一个待办事项应用"）被逐级分解为需求文档、系统设计、模块代码和测试用例，最终产出一个可运行的完整项目。
2. **自动化测试**：测试生成智能体根据需求或代码自动产出测试用例；测试执行智能体负责调度与运行；结果分析智能体解读报告并关联缺陷。三者形成动态闭环，远比静态脚本强大。
3. **代码生成与审查**：部署"开发者"+"审查者"双智能体对抗模式。开发者生成代码，审查者从风格、安全、性能等维度进行批判，两者多轮迭代直至代码达标。
4. **需求分析与系统设计**：需求分析师智能体通过提问澄清模糊需求，系统架构师智能体据此选择架构模式并输出设计图。
5. **智能运维（AIOps）**：监控智能体实时感知异常，诊断智能体定位根因，执行智能体安全地进行扩容、回滚等修复操作。

### 1.5 调研范围与工具选型说明

本次调研聚焦于当前业界和开源社区中，利用大模型驱动多智能体进行软件开发的代表性工具和平台。根据其**抽象层级**与**交付形态**的差异，我们将调研对象分为两大类：

| 类别 | 定义 | 调研工具 |
| :--- | :--- | :--- |
| **底层开发框架** | 提供原子化的智能体构建能力与通信协议，面向开发者 | AutoGen、MetaGPT、smolagents |
| **应用级协作平台** | 将智能体能力封装为 SaaS/PaaS 产品，面向终端用户 | Thingo、秒哒 |

在底层框架中，我们**重点深入研究了 smolagents**，原因如下：
- **极简与透明**：核心代码仅约1000行，不存在过度抽象，适合深入理解智能体协作的本质原理。
- **实验友好性**：支持本地模型，避免 API 费用，便于低成本快速迭代实验。
- **专注核心**：鼓励开发者思考智能体间的通信原语和协作逻辑本身，而非依赖框架预设的复杂模板。

### 1.6 调研方法与评估维度

为了避免本报告仅停留在资料摘录层面，我们在调研过程中采用了“**文档研读 + 源码剖析 + 同构任务实测 + 工程复盘**”四步式方法，尽可能把结论建立在可观察、可比较、可解释的证据之上。

1. **文档研读**：系统阅读各工具的官方文档、GitHub 仓库说明、论文或技术博客，梳理其目标场景、核心概念、工作机制与演进路线。
2. **源码剖析**：对开源框架重点关注其核心抽象是否简洁、控制流是否清晰、二次开发成本是否可控。对于 smolagents，我们额外关注其 ReAct 循环、工具封装方式和多智能体主从调度机制。
3. **同构任务实测**：为了保证横向对比尽可能公平，我们为不同工具设置了尽量一致的三类测试任务，即“前端可视化网页生成”“小游戏生成”“多智能体框架脚本编写”。前两类任务偏向应用层交付，第三类任务偏向框架层抽象能力，用于观察不同工具的能力上界与失效边界。
4. **工程复盘**：除“能不能生成”外，我们还从真实软件工程视角复盘这些工具是否便于调试、是否容易接入现有工具链、是否支持私有化部署、是否适合团队协作与课程项目落地。

基于上述过程，我们将评估维度归纳为以下六项：

- **功能覆盖度**：工具覆盖软件工程生命周期的广度，是否只擅长编码，还是能贯穿需求、设计、测试、部署等环节。
- **透明性与可调试性**：开发者能否看清智能体的思考、执行、报错和中间状态，是否容易定位问题。
- **扩展性与集成能力**：是否便于接入本地模型、第三方工具、数据库、浏览器、MCP Server 及现有研发基础设施。
- **工程可控性**：是否支持权限隔离、代码执行沙箱、日志观测、流程控制等工程级能力。
- **成本与部署门槛**：是否依赖高成本商业模型，是否支持离线或私有化方案，初次搭建复杂度如何。
- **课程项目适配度**：对于时间受限、资源受限但强调理解深度的教学场景，工具是否足够轻量、可解释、便于展示与答辩。

需要特别说明的是，本报告并不试图给出一个脱离场景的“万能最优工具”。我们更关心的是：在 AI4SE 这一仍处于快速演进的方向中，**不同框架分别代表了怎样的技术路线、各自适合解决什么问题、又会在什么边界上失效**。换言之，本报告的目标不是简单排名，而是帮助读者建立一种“带着工程问题意识去看多智能体框架”的分析视角。对于课程学习而言，这种视角往往比单纯记住若干工具名称更有价值；对于后续做项目、写论文或继续扩展系统，也更能形成可迁移的方法论积累。

### 工具一：AutoGen

#### （1）工具名称

**AutoGen** (Automated Multi-Agent Generation Framework)

#### （2）支撑软件开发的阶段

AutoGen 作为一个多智能体协作框架，其能力可以贯穿软件开发的多个阶段。通过模拟不同角色的智能体进行对话和协作来实现自动化，其主要支撑的阶段包括：

- **代码生成与实现**：**这是其最核心、最强的支撑阶段**。通过"程序员"智能体（`AssistantAgent`）和"用户代理"智能体（`UserProxyAgent`）的协作，能够根据自然语言的任务描述直接生成、在本地沙箱中执行并迭代优化代码，形成完整的"生成-执行-纠错"自动化闭环。
- **测试与调试**：可以创建专门的"测试员"智能体（`ReviewerAgent`），由其生成测试用例，并通过代码执行智能体运行测试，实现代码验证和Bug定位。
- **代码审查与优化**：多个智能体之间可以互相审查所生成的代码，从规范性、性能和安全性等角度提出改进建议，形成迭代优化的协作闭环。

#### （3）工具链接

- **官方主页与文档**：[https://microsoft.github.io/autogen/](https://microsoft.github.io/autogen/)
- **GitHub 项目地址**：[https://github.com/microsoft/autogen](https://github.com/microsoft/autogen)

#### （4）工具介绍

**概述与背景**

AutoGen 是由微软研究院推出的一个开源框架，用于构建基于大语言模型的多智能体应用。在大语言模型驱动的多智能体技术快速演进的背景下，AutoGen 凭借其灵活的多智能体协作范式，成为当前 AI 编程辅助、复杂任务自动化领域的代表性工具。该框架聚焦于解决单智能体难以处理的复杂任务场景，通过模拟人类团队协作模式，让不同角色的智能体自主对话、分工协作。AutoGen 的开源属性使其在全球开发者社区中快速迭代，成为多智能体应用落地的重要基础。

**核心架构与工作原理**

AutoGen 的核心是一套轻量化、可定制的多智能体交互与调度体系，其本质可以理解为"面向 LLM 的多智能体协作中间件"。与传统单智能体工具不同，AutoGen 不依赖固定的任务流程模板，而是通过定义智能体的角色、能力边界和交互规则，让多个智能体自主完成任务拆解、分工、执行与迭代。当用户发起一个任务请求后，其工作流分为三个核心阶段：

1. **智能体初始化**：根据任务类型，加载预设的智能体角色。为每个智能体绑定对应的 LLM（如 GPT-4、Claude、本地开源模型）和工具权限（如代码执行、文件读写、网络请求）。
2. **多智能体会话调度**：以 `UserProxyAgent` 为核心交互枢纽，将用户需求转发给 `AssistantAgent`。后者生成初步解决方案（如代码）后，`UserProxyAgent` 自动执行代码并返回结果。若不符合预期，则启动多轮对话，对问题进行定位和优化，直至满足需求。`ReviewerAgent` 可在流程中介入进行规范检查。
3. **任务闭环与结果输出**：所有智能体达成协作共识后，汇总成果，向用户输出最终结果，并记录完整的对话日志与执行记录。

**关键技术特性**

- **多智能体会话**：允许定义多个可定制的智能体（如 `AssistantAgent`, `UserProxyAgent`），并设置一对一、群组（GroupChat）等多种拓扑的会话模式。
- **角色与能力定制**：可以为每个智能体设定不同的系统提示词（System Prompt），绑定不同的底层LLM（混合模型部署），以及授予不同的工具调用权限。
- **无缝代码执行**：`UserProxyAgent` 内置了代码执行器，可直接在本地或容器环境中执行智能体生成的代码片段，并将日志（stdout/stderr）实时反馈给编码智能体。
- **人机协作的自然融入（Human-in-the-loop）**：框架支持在智能体对话的任意环节插入人类干预——当智能体陷入困境时，人类可直接介入对话，提供指令或修改代码。
- **v0.4 架构升级（2025年最新）**：在最新的 v0.4 版本中，AutoGen 引入了全新的异步、事件驱动架构，支持模块化可插拔组件、分布式智能体网络、跨语言支持（Python 和 .NET），以及内置的 OpenTelemetry 可观测性支持和 AutoGen Studio 低代码可视化界面。

**实测任务与能力评估**

为全面评估 AutoGen 的实际能力，我们结合其核心应用场景设计了三个梯度的测试任务：

**任务一：LeetCode 算法题自动求解与验证**
- *任务描述*：要求解决 LeetCode 中等难度的算法题（如"两数相加"），需生成完整的 Python 代码，包含算法实现、边界条件处理、测试用例，并自动执行测试用例验证代码正确性。
- *执行结果*：AutoGen 表现优异。`AssistantAgent` 首先分析题目要求，生成符合逻辑的算法代码；`UserProxyAgent` 执行代码并运行测试用例（包括正常输入、边界输入如空值/极值）；当首次代码存在边界条件遗漏时，`UserProxyAgent` 将报错信息反馈给 `AssistantAgent`，后者自动优化代码，最终代码通过所有测试用例。整个过程无需人类干预，实现了 "理解题目 - 生成代码 - 测试 - 纠错" 的全自动化。

**任务二：数据分析脚本开发与可视化**
- *任务描述*：生成一个 Python 脚本，读取本地 CSV 格式的销售数据，完成数据清洗、统计分析，并生成可视化图表和分析报告。
- *执行结果*：任务完成度高。多智能体协作体现为"数据分析师"+"代码执行器"的分工：前者设计分析流程并生成代码（调用 Pandas、Matplotlib 库），后者执行并反馈问题。经过 2 轮迭代后，脚本成功运行，生成了清晰的可视化图表和结构化的分析报告。

**任务三：自定义多智能体协作框架扩展**
- *任务描述*：基于 AutoGen 的基础架构，扩展一个支持"智能体动态注册/注销"和"任务优先级调度"的自定义框架。
- *执行结果*：AutoGen **未能完成**核心需求。输出仅停留在调用现有 API 实现简单智能体对话的层面，无法实现注册中心、任务队列等框架层扩展功能。此任务失败揭示了其能力边界——它是一个优秀的**应用层**任务执行者，而非**框架层**的创造者。

#### （5）工具评价

**核心优势**

1. **开发效率提升显著**：对于原型验证、脚本编写、数据分析和算法题求解非常高效。"思考-编码-执行-纠错"的自动循环大幅减少了人工来回操作。
2. **协作范式新颖强大**：多智能体对话的模式能处理比单智能体更复杂的任务，模仿了人类团队的工作方式，尤其在需要反复调试验证的编程场景中表现尤为突出。
3. **灵活性极高**：智能体角色、对话流程和工具都可高度定制，能适应从简单的二人组合到复杂的多人群组等多种协作拓扑。
4. **人机协作自然融入**：支持在关键节点插入人类干预，平衡了自动化效率与决策可靠性。

**主要局限**

1. **调试难度高（"黑盒"问题）**：多智能体的对话过程较难追踪，当结果不符合预期时，定位问题根源困难。
2. **Token 消耗成本高**：多轮智能体对话会产生大量 Token 消耗，使用 GPT-4 等付费 API 时成本显著。
3. **框架扩展能力弱**：仅能在预设范式内完成应用层任务，难以满足复杂企业级场景的深度定制需求。
4. **确定性不足**：依赖 LLM 生成质量，对于需要高可靠性的核心生产代码，其结果仍需人工深度审查。

### 工具二：MetaGPT

#### （1）工具名称

**MetaGPT** (Multi-Agent Meta Programming Framework)

#### （2）支撑软件开发的阶段

MetaGPT 是所有调研对象中**对软件开发全生命周期覆盖最完整**的框架。它不仅支撑某个单一阶段，而是通过内置标准化操作流程（SOP）直接驱动了以下所有阶段的连续执行：

- **需求分析**：由产品经理智能体（ProductManager）将用户的一句话需求转化为结构化的产品需求文档（PRD），包含用户故事、竞品分析和需求优先级。
- **系统设计**：由架构师智能体（Architect）根据 PRD 输出完整的系统设计方案，包括类图、数据结构、API 接口定义和技术选型。
- **编码实现**：由工程师智能体（Engineer）根据设计文档逐模块编写代码，代码结构清晰，注释完整。
- **测试验证**：由 QA 工程师智能体（QaEngineer）编写测试用例并执行，形成质量保障闭环。

#### （3）工具链接

- **官方 GitHub 仓库**：[https://github.com/geekan/MetaGPT](https://github.com/geekan/MetaGPT)
- **官方文档**：[https://docs.deepwisdom.ai/](https://docs.deepwisdom.ai/)

#### （4）工具介绍

**核心设计哲学**

MetaGPT 框架的设计哲学核心可以概括为一个简洁而深刻的公式：**Code = SOP(Team)**。这意味着：高质量的代码产出，等于标准化操作流程（SOP）作用于一个专业化的多智能体团队的结果。这一公式揭示了框架的底层逻辑——通过将人类组织中被验证过的分工协作模式系统性地编码到 AI 智能体的交互中，以解决传统多智能体系统协作低效和输出不可控的问题。

**三层架构设计**

MetaGPT 采用了清晰的三层架构：
1. **入口层**：提供 CLI 命令行和程序化接口（如 `generate_repo` 函数），作为用户与框架交互的起点。
2. **核心框架层**：包含团队编排（Team 类）、环境管理（Environment）、角色系统（Role 基类及其子类）和动作系统（Action 基类及 ActionNode），实现智能体协作的核心逻辑。
3. **支撑系统层**：包括 LLM 集成、配置管理、记忆存储、RAG 引擎等基础设施组件。

**核心工作流：一句话生成项目**

当用户输入"Create a 2048 game"这样一条指令后，框架内部的执行流程如下：

1. **ProductManager** 接收指令，执行 `WritePRD` 动作，输出一份完整的 PRD 文档。
2. **Architect** 监听到 PRD 的发布，执行 `WriteDesign` 动作，输出系统设计文档（含类图、API 等）。
3. **ProjectManager** 据此执行 `WriteTasks` 动作，将设计拆解为具体的开发任务列表。
4. **Engineer** 按照任务列表逐一执行 `WriteCode` 动作，生成项目的所有源代码文件。
5. **QaEngineer** 最终执行 `WriteTest` 和 `RunCode` 动作，编写测试用例并运行，验证代码的正确性。

**多智能体交互设计**

框架采用**事件驱动架构**实现组件间的松耦合交互：
- **发布-订阅模式**：角色通过 `publish_message()` 发布事件，通过 `_watch()` 机制订阅和响应相关上游智能体的输出。例如，`SimpleTester` 通过 `self._watch([SimpleWriteCode])` 来监听编码智能体的输出。
- **环境路由**：Environment 组件负责消息的路由和过滤，确保信息准确传递给正确的下游。
- **异步执行**：支持角色和动作的并行处理，提升执行效率。

**核心代码示例**

定义一个自定义动作（Action）：
```python
from metagpt.actions import Action

class SimpleWriteCode(Action):
    PROMPT_TEMPLATE: str = """
    Write a python function that can {instruction}.
    Return ```python your_code_here ``` with NO other texts,
    your code:
    """
    name: str = "SimpleWriteCode"

    async def run(self, instruction: str):
        prompt = self.PROMPT_TEMPLATE.format(instruction=instruction)
        rsp = await self._aask(prompt)
        code_text = SimpleWriteCode.parse_code(rsp)
        return code_text
```

定义一个自定义角色（Role）：
```python
from metagpt.roles import Role

class SimpleCoder(Role):
    name: str = "Alice"
    profile: str = "SimpleCoder"

    def __init__(self, **kwargs):
        super().__init__(**kwargs)
        self.set_actions([SimpleWriteCode])

    async def _act(self) -> Message:
        todo = self.rc.todo
        msg = self.get_memories(k=1)[0]
        code_text = await todo.run(msg.content)
        msg = Message(content=code_text, role=self.profile, cause_by=type(todo))
        return msg
```

创建并运行一个多智能体团队：
```python
from metagpt.team import Team

team = Team()
team.hire([SimpleCoder(), SimpleTester(), SimpleReviewer()])
team.invest(investment=3.0)
team.run_project("write a function that calculates the product of a list")
await team.run(n_round=5)
```

**实测能力评估**

在我们的实测中，使用 MetaGPT 生成 2048 游戏的完整项目。框架从一句话需求出发，经过 ProductManager -> Architect -> ProjectManager -> Engineer -> QaEngineer 的完整流水线，最终在 `./workspace` 目录下生成了包含完整目录结构、HTML/CSS/JavaScript 源文件和测试文件的可直接运行的项目。生成的代码结构清晰、注释完整，为不同数字的格子设计了不同的背景色，游戏状态判断逻辑准确。

#### （5）工具评价

**核心优势**

1. **端到端软件开发的标杆**：在所有调研的框架中，MetaGPT 对软件工程的全生命周期覆盖最为完整和严谨。它不仅生成代码，更生成了贯穿需求、设计和测试的全流程"文档级"交付物。
2. **SOP 驱动的高稳定性**：标准化流程约束了智能体的行为，使其输出的可预测性和一致性远高于自由对话式的框架。结构化通信（通过文档而非纯自然语言）显著降低了信息熵减。
3. **事件驱动的松耦合设计**：`_watch` 和 `publish_message` 机制使得添加新角色或修改流程变得相对容易。

**主要局限**

1. **框架抽象度高，定制灵活性受限**：角色与流程相对固化，扩展至非软件工程领域的通用性较弱。如果项目需要一个 MetaGPT 未预设的角色或非标准流程，修改成本较高。
2. **对底层 LLM 能力高度依赖**：SOP 流程的成功执行，特别是架构设计和代码生成环节，高度依赖底层 LLM（如 GPT-4）的理解和生成能力。如果使用能力较弱的开源模型，流水线可能在中间环节就因生成质量不达标而崩溃。
3. **成本问题**：完整的从需求到测试的流水线调用会产生大量 Token，单次运行的 API 成本可能较高。

### 工具三：smolagents（重点深入）

#### （1）工具名称

**smolagents** (Lightweight Code-Centric Agent Library)

#### （2）支撑软件开发的阶段

smolagents 作为一个通用的底层智能体构建库，其能力覆盖面取决于开发者为其配备的工具和模型。在软件工程场景下，它主要支撑以下阶段：

- **编码实现**：**这是其最核心的支撑阶段**。CodeAgent 直接生成并执行 Python 代码来完成任务，天然适合代码生成、脚本开发、数据处理等编码类工作。
- **测试验证**：可以通过为智能体配备代码检查工具（如 flake8、pylint 的 API 包装），实现代码规范检查和初步测试。
- **需求分析辅助**：通过配备网络搜索工具，智能体可以辅助进行技术选型调研和需求可行性分析。
- **运维辅助**：通过接入 MCP Server，可以连接监控系统、数据库等，辅助日志分析和异常排查。

#### （3）工具链接

- **官方文档**：[https://smolagents.org/](https://smolagents.org/)
- **GitHub 项目地址**：[https://github.com/huggingface/smolagents](https://github.com/huggingface/smolagents)
- **Hugging Face 主页**：[https://huggingface.co/docs/smolagents](https://huggingface.co/docs/smolagents)

#### （4）工具介绍

**概述与设计哲学**

smolagents 是由 Hugging Face 推出的开源 Python 库，其核心设计哲学可以用三个词概括：**极简（Minimal）、透明（Transparent）、代码优先（Code-First）**。在当前 LangChain、AutoGen 等框架日益庞大和复杂的趋势下，smolagents 反其道而行之，刻意将核心逻辑控制在约 1000 行代码之内，去除了过度的中间件抽象，让开发者能够直接面对智能体行为定义的核心——即"一个 LLM 如何通过思考和执行代码来解决问题"。

这种极简主义并非简陋，而是一种精心设计的取舍。正如我们小组在调研中发现的那样：**相比于其他重型框架，smolagents 的核心代码逻辑非常少，我们阅读了其源码，发现其主要基于 ReAct (Reason + Act) 模式进行编排。**这使得它成为了理解 Agent 本质逻辑的最佳教材。

**双核智能体引擎**

smolagents 提供两种主要类型的 Agent 引擎：

1. **CodeAgent（代码智能体，核心主推）**：
   这是框架内首推的、也是最具创新性的智能体类型。在面临任务时，CodeAgent 通过生成一段端到端的 Python 代码片段作为其"行动（Action）"，并直接在受控环境中执行。
   
   *为什么代码优于 JSON？* 这种机制将传统的工具调用自然地转化为代码中的函数调用。它天生支持复杂的控制流结构——循环（`for/while`）、条件分支（`if/else`）、异常捕获（`try/except`）以及局部变量的状态传递。在传统 JSON 范式下，LLM 可能需要与环境进行十几次往返交互才能完成的数据清洗或多步骤推理任务，CodeAgent 往往通过生成一段包含 for 循环和条件判断的 Python 代码并一次性执行即可完成。相关 Benchmark 证明，CodeAgent 的通过率（Pass Rate）比 JSON 工具调用高出约 30%。

2. **ToolCallingAgent（工具调用智能体）**：
   作为传统范式的兼容和补充，为了适应更倾向于标准 API JSON 输出的场景，或者专门针对 JSON 输出微调过的较小模型，smolagents 也完整支持工具调用智能体。

**底层运行机制：纯粹的 ReAct 循环**

在代码层面，smolagents 实现了最经典的 ReAct (Reason + Act) 循环：

1. **Thought（思考）**：LLM 接收任务描述和当前上下文，输出一段"思考过程"的文本，分析问题并规划下一步行动。
2. **Code（代码生成）**：基于思考结果，LLM 生成一段包含工具函数调用的 Python 代码片段。
3. **Observation（观察执行结果）**：框架在沙箱内执行这段代码，并将终端的日志（stdout/stderr）或函数返回值作为 Observation 回传给 LLM。
4. **迭代或结束**：如果任务未完成，LLM 基于 Observation 进入下一轮 Thought-Code-Observation 循环。如果任务完成，智能体在代码中将最终结果赋值给 `final_answer` 变量，任务闭环。

**"三大不可知（Agnostic）"生态集成能力**

smolagents 具备极强的生态包容性：

1. **模型不可知（Model-Agnostic）**：原生支持 Hugging Face Hub (通过 Inference API)、OpenAI、Anthropic 等主流商业 API，同时无缝兼容通过 LiteLLM、Ollama 或 Transformers 库本地部署的开源模型（如 Llama-3、Qwen 等），对于构建断网环境下的私有化工具极为有利。
2. **工具不可知（Tool-Agnostic）**：除了原生 Python 自定义工具外，还能直接加载任何 MCP (Model Context Protocol) Server 的工具、LangChain 格式的工具，甚至是 Hugging Face Hub 上的 Spaces 应用作为工具。最新的 MCP 规范还引入了 `outputSchema` 支持，允许工具返回结构化数据。
3. **多模态不可知（Modality-Agnostic）**：在 VLM 的支持下，智能体能直接接收并处理图像、视频流或音频指令。

**多智能体协作机制**

smolagents 采用了**层级化与代理化（Hierarchical & Delegated）**的编排模式。通过 `ManagedAgent` 类，开发者可以将一个拥有专属系统提示词和垂直领域工具的 Sub-Agent 包装成一个"功能工具"。上层的管理者智能体（Manager Agent）在需要时，像调用普通函数一样"调用"子智能体去解决特定的拆分任务，并获取返回结果。

这种**主从架构（Master-Worker）**避免了多个智能体在群聊中相互推诿和信息发散的通病。它结构清晰易于收敛，并且通过分离不同智能体的记忆（Memory），保证了各局部子系统的专注性，大幅降低了单次调用的 Token 开销。

**安全沙箱机制**

允许 LLM 编写并动态执行代码的最大隐患是系统安全。smolagents 在架构设计之初就将安全沙箱置于显要位置：
- **LocalPythonExecutor**：内置的本地解释器，适用于快速原型验证，但安全限制有限。
- **E2B 沙箱**：连接 E2B 云服务，在完全隔离的云端容器中执行代码。
- **Docker 沙箱**：在本地 Docker 容器中运行，兼顾安全性和私有部署需求。
- **Modal 沙箱**：利用 Modal 的 serverless 容器平台进行隔离执行。

**为什么 smolagents 特别适合本次课程项目**

从课程项目和研究型作业的角度看，smolagents 的价值并不仅在于“能做事”，更在于“便于解释自己为什么这样做”。这一点对课堂展示和答辩尤其重要。相比黑盒程度较高的平台型产品，smolagents 的优势主要体现在以下几方面：

1. **便于做原理级展示**：报告、课堂汇报或答辩时，教师通常不仅关注最终结果，也会追问系统架构、执行流程和技术取舍。smolagents 的主循环清晰，能够较容易地画出执行链路图并解释每个阶段的输入与输出。
2. **便于做局部替换实验**：我们可以只替换模型、只替换工具、只替换提示词，而无需重构整套框架。这种“控制变量式实验”很适合学术训练和课程作业。
3. **便于与本地代码资产融合**：对于已有的 Python 脚本、测试工具、数据处理函数，smolagents 可以非常自然地把它们封装成工具复用，而不用把全部逻辑迁移进某个高度定制的平台。
4. **便于后续自行演化**：如果课程后续要继续扩展成毕业设计、科研课题或团队原型系统，smolagents 的轻量底座更方便逐步叠加需求澄清、计划生成、审查反馈、测试回归等上层模块。

**核心代码示例**

零样板代码的工具定义：
```python
from smolagents import tool

@tool
def check_code_linting(file_path: str) -> str:
    """
    检查指定 Python 文件的代码规范与语法错误。
    Args:
        file_path: 待审查的本地文件路径，例如 "src/main.py"
    """
    import subprocess
    result = subprocess.run(["flake8", file_path], capture_output=True, text=True)
    return result.stdout if result.stdout else "检查通过: 0 errors, 0 warnings."
```

实例化并运行 CodeAgent：
```python
from smolagents import CodeAgent, HfApiModel

agent = CodeAgent(tools=[check_code_linting], model=HfApiModel())
agent.run("帮我检查 data_processor.py 有没有语法问题，并给出修复建议。")
```

搭建 Manager + Sub-Agent 多智能体系统：
```python
from smolagents import CodeAgent, HfApiModel, ManagedAgent

# 创建负责网络搜索的子智能体
search_agent = CodeAgent(tools=[web_search_tool], model=HfApiModel())
managed_search = ManagedAgent(
    agent=search_agent,
    name="search_assistant",
    description="专门通过网络搜索寻找事实或当前信息的智能体。"
)

# 创建管理者智能体
manager = CodeAgent(tools=[], managed_agents=[managed_search], model=HfApiModel())
manager.run("帮我搜索当前最高票房的电影，然后对结果进行分析。")
```

- *过程观察*：失败并不意味着 smolagents 本身设计不好，而是说明当前基于 LLM 的代码智能体在面对“设计抽象接口、建立消息路由、制定调度协议、保证可扩展性”这类高层问题时，仍倾向于给出表面上像框架、实际上只是若干脚本拼接的结果。这也是我们把它定义为“研究与实现底座”，而非“自动框架发明器”的重要原因。

**我们的实测复盘与经验总结**

通过围绕 smolagents 的多轮实验，我们进一步得到如下经验性结论：

1. **任务描述越结构化，完成质量越高**：当提示词中明确给出输入、输出、约束和交付形式时，CodeAgent 往往能够快速收敛；若需求过于抽象，则容易出现“代码能跑但不完全符合意图”的偏差。
2. **工具边界清晰时，智能体更稳定**：若工具只做单一职责，例如“检索信息”“执行测试”“保存文件”，智能体调用时更不易混乱；若工具语义过于宽泛，则会增加错误组合的概率。
3. **代码执行能力是 smolagents 的真正分水岭**：它强的地方不是聊天，而是“通过代码解决问题”。因此接入的底层模型若代码能力不足，即使对话能力不错，也可能严重拖累整体表现。
4. **工程化前必须补足观测和约束**：用于研究演示时，LocalPythonExecutor 足够方便；但若想进入长期项目开发，仍需补充日志记录、运行超时、资源限制、失败重试和沙箱隔离等工程机制。

#### （5）工具评价

**核心优势**

1. **极致的透明度与调试友好性**：核心代码不到 1000 行，整个推理循环一览无余，开发者可以轻松追踪每一步 LLM 生成了什么代码、系统执行后返回了什么。这是一个真正的"玻璃盒"系统。
2. **代码驱动的强组合性**：CodeAgent 可以通过编写 for 循环、列表推导式等复杂逻辑，实现传统 JSON 工具调用无法企及的高效数据处理和逻辑推理。
3. **工具生态极度开放**：原生 Python、MCP Server、LangChain 工具、HuggingFace Spaces 均可作为工具接入，几乎没有任何生态隔阂。
4. **安全沙箱的完备支持**：从本地到 Docker 到云端 E2B，提供了多层次的安全隔离方案。
5. **极低的学习成本与二次开发门槛**：API 接口清晰，极简主义设计使得各类水平的开发者都能快速上手。

**主要局限**

1. **缺乏高级多智能体编排模式**：`ManagedAgent` 仅提供简单的主从调用，不具备 MetaGPT 那样的 SOP 流水线、AutoGen 那样的群组聊天（GroupChat）或消息广播系统。对于需要复杂协作拓扑的场景，开发者需自行实现大量的调度逻辑。
2. **对底层模型的代码能力要求极高**：CodeAgent 依赖 LLM 生成语法正确、逻辑清晰的 Python 代码。如果接入代码能力较弱的开源模型，常常会发生缩进错误、工具参数缺漏等问题，导致执行异常甚至死循环。
3. **沙箱配置的运维门槛**：要在生产环境安全部署，必须配置 Docker 或 E2B 等外部服务，增加了 DevOps 的复杂度。

**综合判断**

综合来看，smolagents 并不是“功能最多”的框架，但它很可能是当前“**最适合作为教学、研究和轻量原型底座**”的框架之一。它的核心竞争力不在于替开发者预先设计好一切，而在于把“如何构建 Agent”这件事尽量还给开发者本人。对于希望真正理解智能体工作机制，而不是仅仅消费一个现成平台的人来说，smolagents 的学习价值和演化空间都非常高。

**秒哒**（百度旗下）

#### （2）支撑软件开发的阶段

秒哒的核心能力是颠覆传统的软件构建流程，它将自然语言描述直接转化为可运行的应用。其支撑作用贯穿并重构了从概念到成品的核心阶段：

- **系统与界面设计**：自动生成符合描述的前端界面布局、组件和基础样式。
- **编码实现**：自动完成前端页面、交互逻辑乃至部分后端接口的代码生成，将"编码"从"编写"变为"描述生成"。
- **部署与测试**：生成的应用可直接运行和预览，部分场景提供一键部署能力。

#### （3）工具链接

#### （4）工具介绍

**平台定位**

秒哒是百度基于文心大模型构建的生成式零代码应用开发平台（Generative No-Code Platform），其核心定位是 **Prompt-to-App**——从一句话需求到可运行 Web 应用的全链路自动化。

**多智能体系统架构分析**

从多智能体系统（MAS）的视角分析，秒哒内部可以解构为以下几大智能体族群：

1. **用户意图理解智能体族群**：
   - 语义解析子智能体：负责理解用户的自然语言需求。
   - 上下文记忆管理子智能体：维护多轮对话中的需求上下文。
   - 情感/风格识别子智能体：捕捉用户对"风格"和"调性"的暗示。

2. **内容生成智能体族群**：
   - 创意启发智能体（发散思维）：产生多种可能的界面和功能方案。
   - 结构化构建智能体（逻辑框架）：将创意收敛为具体的技术方案，生成代码结构。
   - 风格适配智能体：根据用户偏好调整 UI 风格。

3. **质量控制智能体族群**：
   - 连贯性检查智能体：检查生成应用的逻辑流畅性。
   - 实用性验证智能体：验证生成应用的功能是否可用。
   - 伦理合规审查智能体：确保内容安全合规。

4. **协调与管理智能体**：
   - 任务分配协调员：总控任务分发。
   - 资源调度管理器：管理计算资源。
   - 冲突仲裁者：处理智能体输出之间的矛盾。

**多智能体协作机制**

秒哒内部的智能体协作采用了多种机制的组合：
- **瀑布式协作链**：用户输入 → 意图理解 → 创意生成 → 优化调整 → 质量审核 → 输出。
- **竞合式生成模式**：多个生成智能体并行产出不同版本，评估智能体进行投票评分，融合智能体整合最优方案。
- **迭代优化循环**：生成-评估-反馈-再生成的闭环，通过强化学习机制不断优化。

#### （5）工具评价

**核心优势**

1. **将应用开发的边际成本降至最低**：非技术人员也能通过自然语言描述快速生成可运行的 Web 应用，非常适合快速原型验证（MVP）和展示型应用开发。
2. **全栈自动化**：覆盖了 UI 设计、逻辑编写与云端部署的全链路，实现了从"想法"到"应用"的最短路径。
3. **基于文心大模型的多模型混合架构（MoE）**：后台集成前端生成、后端逻辑、数据库设计等专用模型，针对不同子任务调用最合适的模型。

**主要局限**

1. **生成代码的"黑盒"性与可维护性差**：生成的代码通常难以被人类开发者二次维护和迭代，不适合需要长期演进的正式项目。
2. **不具备系统级软件工程能力**：对于复杂的后端逻辑、高并发处理、分布式系统设计等严肃工程需求，秒哒的能力远远不足。
3. **定制化程度有限**：用户只能通过自然语言描述进行调整，无法直接介入底层代码和架构决策。

### 2.6 本组统一实测任务设计与评分标准

为了让不同工具之间的比较尽可能建立在同一基准上，而不是“谁的宣传更充分、谁的案例看起来更炫”，我们在调研中设计了一套统一的任务框架和观察维度。虽然受课程时间与平台可访问性限制，这套评估还不构成严格意义上的 benchmark，但它足以支撑本报告中的大部分相对比较结论。

**统一任务设计原则**如下：

1. **任务必须具备可交付结果**：不能只看智能体“说得好不好”，而要看最终是否真的生成了网页、脚本、游戏或结构化输出。
2. **任务必须覆盖不同抽象层级**：我们故意把任务分为“应用实现类”和“框架抽象类”，用于区分工具是擅长在既有范式下执行，还是具备更强的抽象构建能力。
3. **任务必须便于跨工具迁移**：选题尽量采用所有工具都能理解的自然语言描述，避免因某个平台特有接口导致不公平。
4. **任务必须能够反映软件工程属性**：不仅关注结果好不好看，也关注代码组织、执行稳定性、可解释性和后续可维护性。

基于上述原则，我们设置了三类代表性任务：

- **任务 A：排序算法可视化网页生成**。该任务主要考察工具对“算法逻辑 + 前端交互 + 可视化表达”的综合处理能力。它既不是纯算法题，也不是纯前端美化题，因此可以较好衡量工具在结构明确的小型开发任务中的交付质量。
- **任务 B：2048 小游戏开发**。该任务比任务 A 更强调状态管理、规则一致性和事件驱动逻辑，能反映工具对中小型完整应用的实现能力，也便于观察其在 UI 生成、逻辑组织和交互体验上的表现。
- **任务 C：多智能体框架脚本编写**。该任务故意提升抽象层级，要求工具不只是“写一个应用”，而是尝试“写一个具备框架雏形的系统”。它主要用于测试工具在元级建模、抽象接口设计和系统组织能力上的上限。

在每项任务执行后，我们不直接用“成功/失败”二元结论下判断，而是从以下五个维度进行复盘：

1. **完成度**：是否真正交付了可运行结果，还是只输出了思路、伪代码或残缺文件。
2. **正确性**：输出结果是否满足任务的核心逻辑要求，是否存在明显功能错误、规则缺失或运行失败。
3. **过程透明性**：在执行过程中，我们能否看清其思考链路、工具调用和错误修复过程，是否方便分析原因。
4. **工程可控性**：开发者是否容易插入自己的工具、限制执行权限、调整流程策略或替换模型。
5. **结果可复用性**：生成物是否具备继续维护和二次开发的价值，还是只适合一次性展示。

从最终实测情况看，这套评分框架帮助我们得出了一个非常稳定的观察：**多数工具在任务 A、B 上都能拿出“看起来不错”的结果，但一旦进入任务 C 这类需要更高层抽象设计的场景，差距会迅速拉开，且几乎所有工具都会暴露明显短板。**这也说明，当前多智能体工具真正成熟的能力区间仍然主要集中在应用层自动化，而不是框架层创造。

此外，我们还注意到一个很有意义的现象：同样完成了任务 A 或任务 B，不同工具“完成任务”的方式差异非常大。有的工具依赖预设流程和角色分工，有的依赖多轮会话纠错，有的则依赖一次性生成并执行代码。因此，本报告后续的比较并不只关注“有没有做出来”，还会关注“是以什么代价、在多大程度上可控地做出来”。

### 3.2 核心发现与能力边界分析

通过对五款工具的深度调研和实测，我们总结出了一个贯穿所有工具的核心发现：

> **当前所有基于 LLM 的多智能体工具，都是强大的"应用层问题解决者"，而非"框架层或元级的创造者"。**

这一结论源于我们在所有工具上设计的第三类测试任务（编写多智能体框架脚本）的一致性失败。

| 任务维度 | 任务一/二（成功） | 任务三（失败） |
| :--- | :--- | :--- |
| **任务性质** | 应用层实现："在既定框架内造汽车" | 框架层设计："设计并制造造汽车的机器" |
| **问题边界** | 边界清晰，有大量可参考的现成案例 | 边界抽象，依赖原创性架构设计 |
| **知识依赖** | 垂直领域知识（编程语言、算法） | 元知识（分布式系统、设计模式、调度算法） |
| **思维模式** | 归纳与复现 | 演绎与创造 |

**失败原因深度剖析**：

1. **任务复杂度的质变**：前两类任务属于"在现有范式下解决问题"，本质是对已知解决方案的检索、组合和复现。而第三类任务属于"设计新范式"，需要从零开始构建抽象体系。
2. **训练数据的分布偏差**：LLM 的训练数据中，成熟的应用级代码（如网页、游戏、数据分析脚本）数量庞大，而框架级的架构设计文档和代码极其稀缺。
3. **对"元认知"的缺失**：成功完成应用任务展示了出色的"认知能力"，而框架设计需要的是"元认知能力"——反思、设计和改进认知工具本身的能力。

| 需求分析 | ◯ | ★★★ | ◯ | ★★ | ★★ |
| 系统设计 | ◯ | ★★★ | ◯ | ◯ | ★ |
| 编码实现 | ★★★ | ★★ | ★★★ | ★★ | ★★ |

### 3.4 工程视角下的关键差异解释

如果仅从功能表面看，上述工具似乎都能“让多个智能体合作完成任务”；但从软件工程视角进一步拆开，会发现它们在设计哲学上实际上代表了三种完全不同的路线。

1. **流程预制型路线**：以 MetaGPT 为代表。它预设了较强的软件工程角色分工和 SOP 流水线，因此在“从一句话需求生成较完整项目”这类任务中表现稳定，适合标准化、流程相对清晰的交付场景。但其代价是灵活性较低，自定义异常流程和非标准任务时成本更高。
2. **会话协商型路线**：以 AutoGen 为代表。其优势是通过多轮对话让不同角色互相校验、互相推动，适合需要不断试错、讨论和纠偏的复杂任务。但随着参与角色增多，其对话历史、状态管理和调试成本会快速上升。
3. **代码执行型路线**：以 smolagents 为代表。它把“行动”尽量转化为真实代码执行，因此在脚本生成、文件操作、数据处理、前端小项目搭建等任务中效率很高。它不是最完整的软件工程流水线，却是最容易与现有 Python 工具链融合的一条路线。

进一步说，这三条路线背后体现的是不同的工程价值排序：

- **MetaGPT 优先保证流程完整性**，希望把软件开发过程“标准化”。
- **AutoGen 优先保证协作弹性**，希望把复杂问题留给智能体在对话中动态求解。
- **smolagents 优先保证执行透明性与实现简洁性**，希望开发者保有最大程度的掌控权。

这也是为什么我们在课程项目里最终更看重 smolagents。对课堂项目而言，“可解释、可展示、可修改”往往比“功能最全”更重要；而对企业级完整流水线场景，MetaGPT 或 AutoGen 可能在组织化协作上更有优势。

### 3.5 面向不同场景的选型建议

基于前述对比，我们认为不同团队不应简单追求“最强框架”，而应根据目标、资源和可控性要求做取舍：

1. **若目标是课堂展示、课程设计、方法验证**：优先选择 **smolagents**。理由是结构最清晰、学习成本最低、最适合做源码分析和实验复现。
2. **若目标是从自然语言快速产出完整项目骨架**：优先选择 **MetaGPT**。理由是其角色分工和流水线最完整，适合做“从需求到项目”的标准化生成。
3. **若目标是构建可交互、可反复协商的开发助手**：优先选择 **AutoGen**。理由是其会话式协作非常灵活，适合探索性开发和复杂讨论场景。
4. **若目标是办公场景或面向非技术用户的交付**：优先选择 **Thingo** 或 **秒哒**。理由是门槛低、反馈快、展示效果强，但需要接受黑盒性较高、深度工程控制较弱这一事实。
5. **若目标是后续继续做科研或工程拓展**：建议采用“**smolagents 作为执行底座 + 自定义上层 SOP 管理器**”的方式，因为这种组合最有利于持续演进，而不是被单一平台绑定。

为了让上述分析更直观，我们结合文档调研、源码理解和统一任务实测结果，给出一个面向课程研究场景的相对评分表。需要说明的是，这里的评分不是绝对客观的行业排名，而是站在“软件工程课程项目与研究原型构建”的语境下做出的相对判断。

| 维度 | AutoGen | MetaGPT | smolagents | Thingo | 秒哒 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| 工程完整性 | 4 | 5 | 3 | 2 | 2 |
| 调试透明性 | 2 | 3 | 5 | 2 | 1 |
| 二次开发灵活性 | 4 | 3 | 5 | 1 | 1 |
| 课程项目适配度 | 4 | 4 | 5 | 3 | 3 |
| 非技术用户友好度 | 2 | 2 | 2 | 5 | 5 |
| 私有化与低成本实验潜力 | 3 | 2 | 5 | 2 | 2 |

若从不同目标出发，可以得到不同的“最优解”：

1. **追求最完整的软件工程流水线**：MetaGPT 得分最高，因为它最像一个“自动化软件公司”，流程规范、角色齐全，适合展示需求到实现的全链条生成。
2. **追求最强的研究透明性与可改造性**：smolagents 最突出，因为它把复杂度降到了一个课程项目能够真正掌握和讲清楚的范围内。
3. **追求灵活的智能体协作编程体验**：AutoGen 仍然很有竞争力，尤其适合做对话式的编码助手和多角色交互演示。
4. **追求最强的易用性与展示效果**：Thingo 和秒哒更适合非技术用户，但其工程深度和可解释性明显不足。

因此，如果必须给出一个**面向本课程场景的综合排序**，我们的结论是：

> **smolagents > MetaGPT ≈ AutoGen > Thingo ≈ 秒哒**

这里的含义不是 smolagents 在所有维度上都绝对最强，而是它在“学习成本、解释难度、二次开发空间、实验友好性和课程展示效果”这些课程最看重的维度上达成了最好的综合平衡。这也是本组后续计划继续以 smolagents 为底座推进实验系统开发的关键原因。

### 3.7 从课程原型到工程落地的风险清单

多智能体工具在课程展示阶段通常很“惊艳”，但一旦进入持续开发、多人协作和长期维护阶段，就会出现一系列在课堂演示中不容易暴露的问题。为了让本报告更贴近软件工程语境，我们将潜在风险归纳如下：

1. **需求漂移风险**：在多轮对话或多阶段流水线中，最初的用户需求可能被不断重述、简化甚至误解。若缺少明确的需求冻结机制、验收标准和中间文档沉淀，最终输出可能与真实目标发生偏移。
2. **工具权限失控风险**：具备代码执行和文件读写能力的智能体，如果缺少严格权限边界，可能误删文件、覆盖结果、读取不应访问的数据，甚至执行危险命令。因此“能调用工具”并不等于“可以直接投入真实环境”。
3. **幻觉与伪正确风险**：在应用层任务中，智能体常常会生成“看起来很合理”的代码或解释，但实际上包含细小而关键的逻辑错误。尤其是框架设计、系统架构和接口契约这类高抽象任务，最容易出现结构似是而非的问题。
4. **可维护性风险**：生成代码不等于高质量工程代码。如果没有统一命名规范、模块边界、测试约束和日志机制，后续接手的人往往很难继续维护，导致“首轮生成很快，后续演进很痛苦”。
5. **评估失真风险**：很多演示任务因为本身规模小、目标清晰、验收简单，所以容易让人误以为工具已具备通用工程能力。但当任务转向复杂后端、外部依赖、多用户并发和长期运维时，原先的结论可能并不成立。
6. **人机协作断层风险**：如果团队成员把智能体当作“自动写完一切的黑盒”，而不是当作“可被审查、可被约束、可被复盘的协作者”，就容易在流程中丢失人工判断，最终把错误快速放大。

因此，从工程角度看，真正合理的落地方式不是“完全替代人”，而是把多智能体系统视为一个高效率但需要约束的协同层：它负责加速信息整理、代码草拟、测试生成和初步修复，而人类工程师仍需掌控需求边界、架构选型、质量验收与上线决策。

### 3.8 在真实研发流程中的推荐落位

从更贴近实际的软件研发流程来看，这五类工具并不适合被放在同一个位置上使用。真正高效的做法往往不是“选一个工具包打天下”，而是根据不同阶段的工作性质，把它们放到最适合的环节中。

| 研发阶段 | 更适合的工具 | 原因说明 |
| :--- | :--- | :--- |
| 前期调研与需求澄清 | Thingo、秒哒、AutoGen | 前两者适合快速收集思路、形成展示原型，AutoGen 适合围绕需求进行多轮对话和方案比较 |
| 系统设计与任务拆解 | MetaGPT、AutoGen | MetaGPT 对结构化角色分工和文档链路更友好，AutoGen 适合进行开放式讨论和架构方案权衡 |
| 编码实现与脚本生成 | smolagents、AutoGen | smolagents 在代码执行与文件组织上更直接，AutoGen 在反复纠错和多角色审查方面更灵活 |
| 测试生成与缺陷定位 | AutoGen、smolagents | AutoGen 更适合设计“开发者-审查者”协作回路，smolagents 适合作为可控的测试执行器底座 |
| 快速原型展示 | 秒哒、Thingo、smolagents | 前两者适合面向非技术观众快速展示结果，smolagents 则适合面向技术评审展示执行原理 |

进一步说，若将它们映射到一个典型的课程或小型团队研发流程中，可以得到如下更细的落位建议：

1. **Thingo / 秒哒适合作为“前台工具”**：用于快速收集想法、搭建演示界面、与非技术同学沟通原型。这类工具最大的价值是缩短从“想法”到“可展示结果”的距离。
2. **MetaGPT 适合作为“流程参考系”**：即使团队最终不直接采用它来开发，也可以参考其产品经理、架构师、工程师、测试工程师的角色划分方式，把课程项目的文档与任务分工做得更规范。
3. **AutoGen 适合作为“交互式协作层”**：当团队需要围绕某个复杂问题反复讨论、验证和纠偏时，AutoGen 的会话式多智能体比静态流水线更有弹性。
4. **smolagents 适合作为“执行与实验底座”**：在需要精确控制工具调用、接入本地脚本、构建可解释实验系统时，smolagents 是最适合继续深挖和工程化演化的选择。

这也从另一个角度说明：**工具选型本质上是“系统放置问题”，而不仅是“功能强弱问题”**。一个功能很强但放错位置的框架，往往不如一个能力适中但与任务阶段高度匹配的工具更有效。

## 第四部分：总结与展望

### 4.1 调研核心结论

1. **多智能体系统是 AI4SE 的必然方向**：单点 AI 辅助工具的瓶颈已经显现。只有通过多智能体的分工协作，才能真正实现软件开发全生命周期的端到端自动化，从根本上提升研发效率。

2. **底层框架各有侧重**：
   - **AutoGen** 擅长灵活的对话式编程协作，适合探索性和迭代性强的编码任务。
   - **MetaGPT** 擅长端到端的标准化软件开发流水线，适合从零到一的项目生成。
   - **smolagents** 以极致的轻量和透明取胜，适合学术研究、算法验证和快速原型构建。

3. **应用级平台降低了 AI 使用门槛，但牺牲了灵活性**：Thingo 和秒哒让非技术人员也能利用 AI 驱动的多智能体系统，但用户无法介入底层逻辑，不适合严肃的软件工程任务。

4. **所有工具的共同边界**：当前的 LLM 驱动智能体在面对需要元级认知（如框架设计、创新性理论构建）的任务时普遍失效，这是由训练数据的分布、模型的推理范式和"认知"与"元认知"的根本差异共同决定的。

### 4.2 多智能体框架的技术发展趋势

1. **协作机制向高效化与规模化演进**：未来框架将不断优化通信架构，集中式神经中枢网络将提升信息实时整合效率，分布式通信协议将降低大规模协作的延迟。强化学习与时序信用分配算法的融合，将实现协作策略的动态优化。

2. **工具集成走向标准化与全场景化**：MCP 等统一协议将打破当前不同框架工具接口碎片化的现状，实现工具在不同框架间的无缝迁移与共享。

3. **开发门槛持续降低**：低代码/无代码功能将成为标配（如 AutoGen Studio 的拖拽界面）。更丰富的场景化模板将加速落地。

4. **安全与可控性成为核心优化方向**：随着智能体在金融、医疗等关键领域的落地，权限管理、输入校验、伦理对齐和决策可追溯将成为刚需。

5. **跨生态融合与轻量化并行发展**：主流框架将加强与大模型生态、云平台的深度融合（如 smolagents 与 HuggingFace Hub 的集成），同时轻量化框架将满足边缘设备和小规模场景的部署需求。

### 4.3 我们的后续计划

在接下来的课程实验和课题研究中，我们小组计划：

1. **以 smolagents 为底层执行器节点**：利用其极简、高效、透明的执行优势，构建智能体的基础运行环境。
2. **在此之上封装软件工程 SOP 流水线管理器**：借鉴 MetaGPT 的 SOP 理念，但通过自行实现更轻量的流程编排逻辑，避免重型框架的学习和调试成本。
3. **构建代码自回归修复（Auto-healing Code）系统**：利用双智能体对抗模式（开发者+审查者），实现代码的自动生成、审查和迭代修复。
4. **结合私有化微调代码大模型**：在断网环境下部署私有化代码大模型，打造具有自主知识产权的轻量级研发提效体系。

| 使用者画像 | 推荐工具 | 理由 |
| :--- | :--- | :--- |
| 研究人员、学生 | smolagents | 极低的学习成本，极高的透明度，适合深入理解智能体原理 |

### 4.5 本报告的局限性与后续改进方向

为了保证结论严谨，我们也需要明确指出本报告仍存在以下局限：

1. **定量评估仍然有限**：本次调研更多是“结构化质性分析 + 小规模任务实测”，尚未建立严格的大样本 benchmark 体系，后续可补充任务成功率、执行时间、Token 消耗、报错率等量化指标。
2. **闭源平台的可见性受限**：对于 Thingo、秒哒这类平台，我们只能通过公开材料和外部使用体验进行分析，无法像开源框架一样深入到底层实现细节，因此相关结论天然带有“黑盒观察”特征。
3. **模型差异会影响结果表现**：同一框架接入不同底层模型时，实际效果可能差异很大。尤其对 smolagents 而言，底层模型的代码生成能力几乎直接决定了上层表现。
4. **测试任务仍偏向课程与原型场景**：我们选择的任务有利于比较工具在应用层交付上的表现，但对大型团队协作、长期维护、复杂后端服务治理等工业级场景覆盖仍不充分。

后续如果继续深化本课题，我们计划从两个方向推进：其一，构建统一的测评基线，对不同模型和不同框架进行可重复实验；其二，在 smolagents 之上继续补齐需求澄清、记忆管理、审查反馈、回归测试与日志追踪机制，把它从“好用的轻量框架”逐步扩展成“适合软件工程研究的可控实验平台”。

### 4.6 面向课程项目的阶段性实施路线图

如果以一个学期内的课程实验为边界，我们认为基于 smolagents 的系统构建可以分为四个阶段推进，每个阶段都有明确目标和可交付成果：

1. **第一阶段：最小可运行原型搭建**
   - 目标：完成单个 `CodeAgent` 的本地运行，打通基本模型调用、工具定义和文件输出流程。
   - 交付物：可执行的最小 demo、基础工具函数集合、运行说明文档。
   - 关注点：先验证“能跑通”，不要过早追求复杂架构。

2. **第二阶段：加入计划与审查机制**
   - 目标：在执行层之上加入任务分解、代码检查、错误重试和简单测试回路。
   - 交付物：具备“生成-执行-检查-反馈”闭环的增强版智能体系统。
   - 关注点：开始记录中间状态，让系统具备可解释性，而不是只关心最终答案。

3. **第三阶段：扩展为多智能体协作结构**
   - 目标：引入 Manager-Agent、测试子代理、检索子代理等组件，形成主从式协作网络。
   - 交付物：具备任务分派、结果汇总和子代理职责划分的多智能体原型。
   - 关注点：避免一开始就设计过度复杂的通信机制，优先采用层级化、收敛快的结构。

4. **第四阶段：补齐工程化要素并形成展示材料**
   - 目标：加入日志记录、失败案例分析、对比实验、答辩可视化材料和最终总结。
   - 交付物：课程报告、演示视频、关键截图、实验结论表格以及后续演化计划。
   - 关注点：不仅证明系统“可运行”，还要证明设计“有依据”、结论“可解释”。

这一路线图的核心思想是：**先做小、再做稳、最后再做复杂**。对于学生团队来说，过早追求全功能、多角色、大而全的平台最容易导致项目失控；而从一个可解释、可调试、可持续扩展的轻量原型出发，反而更容易做出质量扎实、展示效果好的成果。

### 4.7 面向课程答辩的展示亮点建议

从课程答辩的角度看，一份好的调研报告不仅要“写得多”，还要能够在展示时快速体现你们确实做了深入工作。基于本次报告内容，我们认为以下几个展示点最容易形成亮点：

1. **展示方法论，而不是只展示结果**：可以先说明本组并非简单罗列工具介绍，而是采用了“文档研读、源码剖析、统一任务实测、工程复盘”四步法。这会让老师感受到你们的工作是有研究设计的。
2. **突出 smolagents 的源码级理解**：相比直接演示某个平台生成了什么页面，更能体现技术深度的是讲清楚 `CodeAgent`、ReAct 循环、`ManagedAgent` 和沙箱机制分别解决了什么问题。
3. **展示成功案例与失败案例并存**：只展示成功会显得像宣传稿，而把“多智能体框架脚本生成失败”这类案例拿出来分析，更能体现研究的真实性和批判性。
4. **用统一评价表体现比较公平性**：把三类任务、五个评估维度和综合评分表放到答辩 PPT 中，能够显著增强报告的说服力。
5. **把结论落到“为什么我们选 smolagents”**：老师通常会追问“你们为什么最后重点做这个”。此时可从透明性、学习成本、可扩展性、课程适配度和后续演化空间五个角度进行回答。

如果答辩时间允许，建议演示顺序采用“问题提出 -> 为什么要研究 MAS -> 统一实测任务 -> 重点讲 smolagents -> 横向对比 -> 后续计划”这一条主线。这样逻辑会非常顺，既能体现技术深度，也能体现项目推进思路，而不是让整场展示变成工具百科的堆砌。

另外，在展示页面或 PPT 设计上，也建议尽量做到“**一页只讲一个判断**”。例如，一页专门讲“为什么单点 AI 工具不足”，一页专门讲“为什么 smolagents 适合作为底座”，一页专门讲“三类任务与五项评价维度”，最后再用一页收束为结论和后续路线。这样的结构比把所有工具特性堆在一起更容易让评审快速抓住重点，也更能凸显你们做的是一项有方法、有实验、有选择依据的研究工作。
若再配合 1 到 2 个真实运行截图或日志片段，整体说服力通常会再明显上一个台阶，也更利于现场问答展开。

### 附录 B：关键术语说明

- **Agent（智能体）**：能够感知环境、调用工具、执行动作并产出结果的自主软件实体。在 LLM 场景下，通常由模型、提示词、工具、记忆和执行循环共同组成。
- **MAS（Multi-Agent System，多智能体系统）**：由多个智能体共同组成的协作系统，各智能体可承担不同角色，通过消息传递、任务分解或层级调度完成复杂目标。
- **ReAct**：Reason + Act 的缩写，指模型先进行推理，再执行动作，并根据环境反馈继续迭代的工作模式。
- **CodeAgent**：以“生成并执行代码”作为主要行动方式的智能体，相比传统 JSON 工具调用更擅长处理复杂控制流和组合逻辑。
- **ToolCallingAgent**：以结构化工具调用为主要行动方式的智能体，通常更适合 API 明确、动作边界清晰的场景。
- **ManagedAgent**：被上层智能体作为“专用工具”调度的子代理，常用于把复杂任务拆分给更专门的执行单元。
- **MCP（Model Context Protocol）**：一种模型与外部工具或上下文服务交互的标准协议，用于增强智能体对外部系统的连接能力。
- **SOP（Standard Operating Procedure）**：标准操作流程。在多智能体框架中，常被用于约束不同角色的工作顺序、输入输出和责任边界。
- **Human-in-the-loop**：人类参与回路，指在人机协作系统中保留人工监督、审批、纠偏或决策环节，以提升可靠性与可控性。

### 附录 C：本组可复现实验建议

为了便于后续同学或其他小组复现本报告的主要结论，我们建议在实验复现时遵循以下原则：

1. **尽量保持任务描述一致**：不同工具输入的任务提示词应尽量保持同构，避免因为提示词差异导致结论失真。
2. **保留中间过程截图或日志**：不要只保存最终结果页面，还要保存执行过程、报错信息和修改前后版本，便于后续分析。
3. **对“完成”设置最低验收标准**：例如网页必须可交互、小游戏必须可玩、脚本必须能运行，而不是仅有静态代码文本。
4. **区分一次性成功与多轮修复成功**：有些工具首轮结果较差，但在多轮反馈中能逐步收敛；这一差异本身也是重要结论。
5. **记录人工介入成本**：如果某个工具需要大量人工补充说明、反复纠偏甚至手动修改代码后才能成功，则应把这些额外成本纳入评估，而不能只看最终表面效果。
6. **从“是否适合你的场景”出发下结论**：不要简单追求统一排名，而要根据课程任务、团队技能结构、时间预算和设备条件做选择。

### 附录 D：可直接用于汇报的结论提炼

若需要将本报告进一步压缩为课堂汇报中的 1 分钟总结，可以提炼为以下几句话：

1. 当前多智能体工具已经能显著提升应用层开发效率，但距离真正稳定可靠的“自动软件工程师团队”仍有明显差距。
2. AutoGen 强在灵活协商，MetaGPT 强在流程完整，smolagents 强在透明轻量，Thingo 和秒哒强在低门槛和快速展示。
3. 从课程项目和研究原型角度看，smolagents 由于易理解、易调试、易扩展，最适合作为本组后续实验底座。
4. 真正有价值的不是单纯比较“谁更强”，而是理解不同工具适合放在软件工程链路的哪个位置。
5. 多智能体未来最重要的发展方向，不只是更会生成代码，而是更可控、更可解释、更能融入真实工程流程。
